# Narrative Design

## Сначала задайте не блоки, а изменение состояния читателя

До чтения: «Я не понимаю, чем студия может помочь». После: «Вот какую конкретную задачу она решает; вот доказательство; я понимаю, как обратиться».

Для технического читателя другое состояние: «Вижу, что понимают мой процесс, не путают архитектуру и внедрение и знают, как можно проверить систему».

## Четыре драматургические схемы (выбирай, не смешивай все подряд)

**1. Сцена → вопрос → решение → проявление → разговор**. Подходит для иммерсивного проекта и творческого портфолио.

**2. Ограничение → развилка → конструкция → роль человека → следующая проверка**. Подходит для AI, технического продукта, инженерии.

**3. Ситуация читателя → изменение выбора → инструменты → пример → первый шаг**. Подходит для страницы услуги.

**4. Коллекция разных миров → общая логика → независимые практики → приглашение к своей задаче**. Подходит для главной многопрофильной студии.

## Кейсы

Кейс начинается не с «клиент — задачи — решение», а с реального напряжения. При этом *редакторская реконструкция мотива* не выдаётся за цитату клиента. Укажи проблему, решение, собственный вклад, устройство результата и стадию. Метрики — только подтверждённые; отсутствие KPI не делает историю слабой.

Пример для Synapto: специалист не обязан доверять одному баллу. Архитектура AI-платформы для фармацевтических компаний и отдельный интерфейсный прототип показывают, как можно спроектировать проверяемый научный процесс. Пилот на истории компании — предложенный следующий этап, а не состоявшийся результат.

## Ритм

Меняй масштаб: крупный заголовок → маленькая точная деталь → спокойное объяснение → работа → следующий шаг. Переходы должны быть логическими, а не одинаковыми CTA. Страница не обязана иметь один и тот же набор секций, если у неё другая задача.
